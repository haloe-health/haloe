# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Marketing site + booking flow for **haloe**, a hijama/cupping & massage wellness business in Manchester serving women and men. (The booking flow no longer collects gender or surfaces a chaperone requirement — Halima now handles that in person with clients; `chaperone-policy.html` was removed in Sep 2026, don't reintroduce a link to it.) Everything lives under `website-and-booking/`. There is no build step, framework, package manager, or test suite — the site is hand-written static HTML with inline `<style>` and inline `<script>`, plus a handful of Cloudflare Pages Functions and a Supabase (Postgres) database. (D1 was used for booking slot reservation until Sep 2026 — see the migration note under Slot reservation below. It's no longer used anywhere in this codebase.)

**Service model: Weekly Clinic Day: Tuesdays at Milton Hall, 244 Deansgate (Remedy Lounge), full day. Mobile visits across Greater Manchester on other days.** (see `CLINIC_VENUE_NAME`/`CLINIC_WEEKDAY`/etc. constants in `book.html`, `index.html` and the Functions — `CLINIC_START_DATE` is `'2026-10-06'`, the first bookable Tuesday, confirmed by Halima after her venue viewing; before this constant was set, the calendar showed no bookable clinic dates at all rather than defaulting to the next Tuesday, so if it's ever unset again expect that same fail-closed behaviour, not an error). The booking flow has a **Where step** (clinic / mobile) before date & time. **All bookings — clinic and mobile — are paid in full at checkout. There is no deposit option; do not reintroduce a deposit path.** Clinic bookings have no travel fee and no client address (just the venue address and a check-in note); mobile bookings keep the existing calendar and address fields, plus a postcode-driven, zone-based travel fee (see Travel cost below). Do not remove the Where step, and do not add any further clinic locations without confirming with Halima first.

**Cancellation policy (all bookings):** "Free reschedule or full refund up to 48 hours before your session. Inside 48 hours, sessions are non-refundable but can be moved once. No-shows are charged in full." This replaced the old £25-deposit cancellation wording — keep it identical everywhere it appears (`book.html`, `index.html`, `booking-confirmed.html`, `before-your-session.html`, the Stripe checkout description, and the confirmation emails).

**Travel cost (mobile bookings only — Sep 2026, replaced the old "actual cost of a taxi, confirmed after booking" policy):** zone-based on the postcode the customer enters on the Where step, calculated automatically and charged online as its own Stripe line item — no longer a manual, post-booking WhatsApp conversation for Zones A/B. Zone A (£15) is `OL1`–`OL16` plus `M9`/`M24`/`M35`/`M40`/`M43`; Zone B (£35) is every other `M`/`SK`/`BL`/`WN`/`WA` postcode; Zone C (any other postcode) is still allowed but has no fixed online fee — the booking gets a £0 "confirmed by WhatsApp" travel line instead, and is flagged in Halima's notification email and the app so she follows up before the session. The zone logic lives in `functions/_travel.js`, mirrored in `book.html` (browser JS can't import that module — same pattern as `_clinic.js`/`_services.js`). **Travel is never discounted** — `create-checkout.js` computes the treatment amount (and applies any discount code to it) before travel is computed or added anywhere, so a discount code has no code path that could reach the travel line. The public-facing copy — "Home visits: £15 travel in Oldham and nearby, £35 across the rest of Greater Manchester. Or come to our Tuesday clinic on Deansgate — no travel fee." — appears in `book.html` (Step 1), `index.html` (hidden booking widget) and `before-your-session.html`; keep it identical. `booking-confirmed.html`'s "Halima will be in touch" copy is dynamic instead (different for clinic / Zone A·B / Zone C), since travel is usually already paid by the time that page loads.

**Multi-treatment bookings (Oct 2026):** a client can select several treatments in `book.html` (`state.cart`, `toggleService()`); they're done back to back in ONE slot, sized to the summed durations, charged as ONE treatment Stripe line (price = sum, HALOE20 applies to the sum, travel still separate and never discounted). The client posts `treatments: [{name, category}]`; `create-checkout.js`/`apply-discount.js` resolve it with `resolveCart()` in `_services.js` and never trust client prices/durations (old single `treatmentName`/`treatmentCategory` bodies still work). A package can't be combined with anything else. The booking row keeps the joined display name in `treatment` (`A + B`) and the full list in the nullable `bookings.treatments` jsonb column (null for single-treatment/old rows); the webhook and emails split `metadata[treatmentName]` on `' + '`. **Run the `treatments` migration in `supabase-bookings-schema.sql` before deploying** — `listBookings()` selects that column. **Turnaround buffer (Oct 2026):** every booking, clinic and mobile, blocks its treatment length **plus `TURNAROUND_MIN` (15 min, `functions/_slots.js`)**. `generateSlots()` adds it to the candidate slot, and `create-checkout.js` stores `end_min = start + length + 15` — so `bookings.end_min` means "blocked until", not "treatment ends", and `reserve_slot` needed no change. The client only ever sees the real length (summary, emails, admin); `book.html` sends the real duration and the server adds the gap, so there's no mirrored constant in the browser. The calendar buffer itself is separate from the **Milton Hall closing rule** (below), which has its own tidy-up setting. Older bookings made before this have no buffer. Packages are 75 min on both client (`sessionMin`) and server (`min`); `tools/test-slots.js` fails if any client/server duration drifts. There is no travel *time* in availability (only a travel fee).

### Slot reservation / double-booking prevention (Supabase `bookings` table)
- **Migrated from Cloudflare D1 to Supabase (Postgres) in Sep 2026** — no data carried over; the only D1 rows were Halima's own £1 live-mode tests, deleted rather than migrated. The schema lives in `supabase-bookings-schema.sql` at the repo root: `id`, `booking_date` (native `date`), `start_min`/`end_min` (minutes from midnight), `treatment`, `customer_name`/`email`/`phone`, `location` (`'clinic'|'mobile'`), `address` (clinic venue string or the client's mobile address), `amount_pence`, status `'pending'|'confirmed'`, `hold_expires_at` (unix seconds — deliberately kept as bigint, not `timestamptz`, so the existing `HOLD_SECONDS`/`Date.now()/1000` arithmetic didn't need to change). No `stripe_session_id` column this time — the D1 one was dead (defined, never populated or read).
- **D1/SQLite serializes all writes, so a plain "check-then-insert" was atomic there for free. Postgres has real concurrent writers, so it is NOT safe to run the overlap check and the insert as two separate REST calls** — two simultaneous requests could both pass the check before either commits. `reserveSlot()` in `_bookings.js` instead calls a Postgres function, `reserve_slot` (defined in the schema file, invoked via Supabase's RPC endpoint `POST /rest/v1/rpc/reserve_slot`), which takes a transaction-scoped advisory lock keyed by `booking_date` before checking for overlap — every reservation attempt for the same day is serialized, replicating D1's guarantee without serializing different days against each other. **If you ever touch `reserveSlot()`, keep the check-and-insert inside that one Postgres function — do not "simplify" it back into two REST calls from the Worker, that reopens the race.**
- `create-checkout.js` reserves the slot **before** creating the Stripe session. A win writes a `'pending'` row held for `HOLD_SECONDS` (35 min) and passes `metadata[bookingId]` + `expires_at` to Stripe. A loss (the RPC returns `null`) returns **409 `slot_taken`**, and `book.html` sends the customer back to pick another time. Stripe failure releases the hold.
- `stripe-webhook.js` flips the row to `'confirmed'` on `checkout.session.completed`. Abandoned checkouts never confirm; their holds lapse and the overlap check ignores expired pending rows, so the slot frees itself.
- **Fail-open everywhere:** if `SUPABASE_URL`/`SUPABASE_SERVICE_ROLE_KEY` aren't set or the time can't be parsed, checkout proceeds unreserved rather than blocking a paying customer.

### Booking → payment → notification flow (the critical path)
1. `book.html` collects selection + details into `state`, then `handlePayment()` POSTs to `/create-checkout`. Every booking is paid in full — there is no deposit type or amount to choose.
2. The function creates the Checkout Session and sets `success_url` to `booking-confirmed.html` with booking details as query params.
3. **Notification is automatic and does not depend on the customer.** Stripe calls `/stripe-webhook`, which emails Halima and the customer (and would WhatsApp Halima if Twilio were configured — it deliberately isn't). Nothing on the confirmation page is required for Halima to find out about a booking.
4. The WhatsApp alert comes from the Twilio business number, **not** the client's number — sending as the client is impossible and would be impersonation. The client's number is in the message body so Halima can reply.

### Design language (all customer-facing pages)
Reusable patterns are documented in **`COMPONENTS.md`** (repo root) — copy-paste snippets, since the site keeps CSS/JS inline per page. Update that file first when you improve one.

`book.html` and `booking-confirmed.html` share one Apple-derived language (`intake.html` left it in Oct 2026 — see its calm redesign above) — **true black, neutral greys (`#1C1C1E` surfaces, `rgba(255,255,255,0.10)` hairlines), gold used only for the active selection**, sentence-case headings with full stops, and `html { font-size: 78% }` as the single scale dial. Patterns to reuse rather than reinvent:
- **Grouped inset lists** (iOS Settings): label left, answer right, hairline between rows, 12px radius. Build them with a **`.group` wrapper that owns the card**, not per-row `:has()` adjacency rules.
- **Segmented controls** for either/or answers; **toggle switches** for consents. Use a segmented control for anything that reads as a *question* — a lone switch among questions looks out of place. Options must have **no border**; `intake.html` carries a legacy `.opt span` gold hairline that the Apple override has to reset explicitly.
- **There is no pure white in the palette.** The lightest tokens are `--cream` / `--a-t1` (`#F5F0E8`) and `--white` (`#f7f2ea`), both warm. A `#fff` toggle knob on a warm gold track reads as a foreign object — use `var(--cream)`.
- **Pill buttons** — gold fill for the primary action, neutral outline for the secondary.
- Validation sits **under the field it refers to**, with the hairline above it suppressed so field and message read as one cell.
- `book.html` drives steps from a **frosted footer**; its button proxies each step's hidden `#btn-stepN`, so the original validation still governs it.

### Privacy: the client's address
The address collected at step 3 is deliberately **kept out of the URL**. It travels to Stripe as `metadata[customerAddress]`, and reaches `booking-confirmed.html` via `sessionStorage` (`haloe_address`). Never add it to `success_url` — home addresses in URLs leak into browser history, referrer headers and server logs.

## Compliance (client-facing copy)

- **All client-facing copy must use wellness/symptom language only.** Never claim — explicitly or by implication — to **treat, cure, manage, or heal a named medical condition** (e.g. arthritis, migraine, depression, infertility, IBS, sciatica, etc.). This applies to every customer-visible string: `index.html`, `book.html`, `booking-confirmed.html`, meta descriptions, alt text, and any Stripe/WhatsApp message copy.
- Frame benefits as supporting wellbeing or easing symptoms/sensations, not as medical intervention. Prefer "may help with tension, aches, and relaxation" over "treats back pain"; prefer "supports general wellbeing" over "manages anxiety".
- When editing or adding copy, audit it against this rule before committing. If asked to add a condition-specific claim, push back and reword it into compliant symptom/wellness language.
- Claims removed in July 2026, for reference on what the rule catches: *"draws out stagnant blood, toxins, and impurities to restore the body's natural balance"* (physiological claim), *"one of the oldest and most powerful forms of natural medicine"* (calls it medicine, asserts potency), and a hero line *"addressing pain, hormonal health, fatigue"* (names conditions).

## Conventions & gotchas

- Keep CSS/JS inline in each HTML file — that's the established pattern. **One deliberate exception**: `services-data.js` (`SERVICES`/`PROMO_DISCOUNT`/`netPrice()`, loaded by `book.html` and `hijama-manchester.html` — `index.html`'s widget keeps its own separate `HB_SERVICES`/`HB_PROMO_DISCOUNT`, predates this file). Don't "helpfully" re-inline it back into a page — that reintroduces the exact drift/duplication it exists to prevent.
- **The custom bee cursor (`cursor.js`/`cursor.css`, plus its `cursor-bee.svg`/`cursor-bee-pointer.svg` source art) was removed entirely in Sep 2026** — every page uses the plain system cursor now. Don't reintroduce it or its `<link>`/`<script>` tags.
- **Hover styles must be guarded for touch.** On a phone `:hover` sticks to the last-tapped element. A `:hover` rule that out-specifies `.selected` (e.g. `.time-slot:hover` set gold text, `.time-slot.selected` set black) leaves the selection invisible after a tap — the picked slot rendered gold-on-gold. Wrap interactive hover states in `@media (hover: hover)` **and** add `:not(.selected)`. This bit `.time-slot` and `.cal-day` in `book.html`.
- **Autofill fields need an override or they show pale yellow.** Safari/Chrome ignore `background-color` and `color` on an autofilled field. Cover it with an inset `box-shadow` matching the field's surface plus `-webkit-text-fill-color`, and a `transition: background-color 100000s` so the yellow doesn't flash back. Present in all three forms; the inset colour differs per form (see each `:-webkit-autofill` block). On `book.html` the real step-3 fields are `.ios-row` (transparent inputs on a `#1C1C1E` card), **not** the legacy `.form-field` — match the card colour. An `.invalid` row signals with red text, so it keeps `-webkit-text-fill-color: #E5736A`.
- Design tokens are CSS custom properties redefined per file (`--gold #C8A96E`, `--black #0D0D0D`, `--cream #F5F0E8`). Reuse them rather than hard-coding colours. Font is Poppins via Google Fonts.
- **The real WhatsApp number is `447474833643`** — used everywhere. Never reintroduce the old `447700000000` placeholder.
- **The Instagram handle is `@haloe.health`.** The old `@haloe_hijama` survived in six places until July 2026 (the intake guide email, `before-your-session.html`, the homepage footer, the intake error message). Don't reintroduce it.
- **`book.html`'s pay-note promising a WhatsApp confirmation is correct copy, not a bug.** Twilio is inert, so it looks like a broken promise and is tempting to rewrite as email — but Halima messages every client on WhatsApp **herself**. Leave it.
- **The intake form is deliberately not linked or prompted anywhere.** Halima speaks to each client on WhatsApp first and sends `haloe.health/intake` herself. The automatic prompts were removed from all four places that had them — the customer email in `stripe-webhook.js`, `booking-confirmed.html`, `book.html` and `index.html`. The form is still live and still writes to D1; only the prompts are gone. **Do not "helpfully" re-add a link.** (One deliberate exception, Oct 2026: `before-your-session.html` tells clients to fill in the form and links `haloe.health/intake`, at Halima's explicit request.) `stripe-webhook.js` carries a comment showing how to restore the email block when she wants it back.
- If you change a price or treatment name, update `services-data.js` (drives both `book.html` and `hijama-manchester.html` automatically), **`HB_SERVICES` in `index.html`**, and **`functions/_services.js`** — three separate places, none of which can import another. `HB_SERVICES` predates `services-data.js` and has silently diverged before (it once advertised facials and peels that were never offered); `_services.js` is what `create-checkout.js` actually charges, so a missed update there means Stripe charges the old price even though the UI shows the new one.
- **The site-wide promotional discount is OFF.** `PROMO_DISCOUNT` (`services-data.js`), `HB_PROMO_DISCOUNT` (`index.html`'s widget) and their mirror in `functions/_services.js` are all `0`, so `netPrice()`/`hbNet()` just return the full list price and no strikethrough renders. The machinery is intact for a future promo: set the constants to e.g. `0.2` — **all three, they can't import each other** — and the struck-through prices come back with no other edit. **Never read `svc.price` for money** either way; `netPrice()` is always the figure displayed and charged.
- **The only live discount is the HALOE20 launch code** — 20% off **all treatments** (not just a customer's first booking), expiring 31 Oct 2026 23:59 UK time. It is **not** a site-wide promo: the customer types it on step 5 of `book.html`, `/apply-discount` previews it, and `create-checkout.js` re-validates and recomputes from scratch at payment time, never trusting the preview. The code, its percent, its expiry and its `single_use_per_email` flag are **rows in Supabase's `discount_codes` table** (`supabase-discounts-schema.sql`), not constants in the repo — so changing the terms, or adding another code, is a SQL statement, not a deploy. HALOE20 is **reusable without limit** (same person, any number of times) until it expires at 31 Oct 2026 23:59:59 UK: its row has no `max_uses_*` caps, and promo redemptions are written with `code_redemptions.enforce_limits = false` so the unique indexes (which used to cap EVERY code at one use per code/email) ignore them — if you add another promo code, `type = 'promo'` is what makes it reusable. `single_use_per_email` is `false` for HALOE20; the one-redemption-per-email branch in `functions/_discounts.js` stays for any future code that wants it. **A discount only ever touches the treatment price** — see Travel cost above. The public copy ("Launch offer: 20% off all treatments until 31 October 2026. Use code HALOE20 at checkout.") appears in `index.html`'s promo banner, `book.html` step 5 and `hijama-manchester.html`'s price intro; keep it identical, and keep it in step with the row's real expiry.
- Mobile calendar disables past dates and Sundays; clinic calendar disables everything except `CLINIC_WEEKDAY` on/after `CLINIC_START_DATE` (see Service model). Mobile time slots are a fixed hard-coded list, 10:00–20:00 in 30-minute steps, duplicated in both `book.html` and `index.html`; clinic time slots come from `CLINIC_SLOT_TEMPLATE`, duplicated the same way.
- **`book.html` slots now reflect real availability** — on date select it fetches `/availability`, then greys out any slot that would overlap an existing booking given the selected treatment's duration (parsed from its `time`). Changing treatment re-validates the chosen slot on return to step 2. It also disables any time **earlier than now when the chosen day is today** (`slotIsPast`), so this-morning's slots can't be booked. The homepage widget does **not** do this (see reservation section above).
- The site serves extensionless URLs — `/book.html` redirects to `/book`. Query strings survive the redirect, but `curl` needs `-L` or you'll read an empty 308 and wrongly conclude a deploy failed.
